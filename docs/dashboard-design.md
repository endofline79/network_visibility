# Custom dashboard direction

Status: implemented and deployed after approval on 2026-09-20 UTC. The running
collector was not restarted or reconfigured. The custom web app combines a
world map/globe with traditional log views. See [operations](dashboard.md).

## Application

One additional Compose service on AI-02: a compiled React/TypeScript frontend
served by a Python FastAPI backend. The backend queries VictoriaLogs over the
internal Docker network. Keep the raw VictoriaLogs API private and apply bounded
time ranges, limits, and timeouts to application queries. The new service should
not need OPNsense administrative credentials.

## Visual experience

- A prominent world map with connections between the lab and observed public
  endpoints. Offer a globe presentation as an alternative to the flat map.
- Distinguish allowed and blocked events with labels and line styles as well as
  color. A blocked connection is not automatically an attack.
- Selecting a country, endpoint, or device filters the accompanying event table.
  Keep a dedicated Events view for focused investigation and raw message detail.
- Use subtle activity animation tied to new observations, with pause and reduced
  motion support. Historical views should use a clearly labeled time window.
- Display freshness, collection gaps, and coverage separately from activity.

The original in-conversation concept uses eight fictional events, reserved example IPs,
published country geometry, and country centroids. It contains no live network
data, and its counts and locations must not be reused as production fixtures.
Country/action filtering, empty results, view switching, globe presentation, and
desktop/mobile rendering were checked in an isolated headless browser.

## Implemented data handling

1. Parse OPNsense filterlog CSV into validated fields: timestamp, interface, rule,
   action, IP version, protocol, source/destination addresses and ports. Cover
   IPv4, IPv6, and protocol-specific variations; preserve the raw message and
   account for parsing failures instead of silently omitting them.
2. Enrich public addresses with a locally stored IP geolocation database. Do not
   send observed IP addresses to a third-party lookup API. Keep private,
   non-routable, and unlocated addresses in the log view and coverage counts.
3. Treat geographic coordinates as approximate endpoint locations, and map
   lines as connections rather than actual packet routes. Do not infer a person,
   exact street address, threat level, or service identity from location alone.
4. DB-IP Lite supplies local geolocation; it is downloadable as MMDB,
   updates monthly, and requires attribution on pages using its results. Bundle
   map assets with the real app, and surface database age and lookup coverage.

## Traffic coverage

The existing syslog input includes only events generated by current logging
settings. Map line weight initially represents logged event counts, not bytes,
active sessions, or complete traffic volume. No firewall rule logging was changed
for this concept.

To add bandwidth and wider flow visibility, inspect and configure OPNsense NetFlow
export and a separate collector as a subsequent change. Choose observation
interfaces deliberately, preserve useful pre-NAT device identity, and validate
against interface counters to avoid double counting. Traffic that never crosses
OPNsense requires another observation point, such as switch telemetry or mirroring.

Sources checked on 2026-09-20 UTC:

- [OPNsense NetFlow export and analysis](https://docs.opnsense.org/manual/netflow.html)
- [DB-IP Lite downloads and attribution](https://db-ip.com/db/lite.php)
- [D3 Maps Atlas country geometry](https://esm.sh/@d3-maps/atlas@1.0.0/world/countries/countries-110m)

The deployed app uses real collector data and a verified local DB-IP Lite database.
It does not use the concept's fictional events. The user selected Rochester, NY
as the city-level lab anchor. No flow export, firewall rule logging, third-party
lookup of observed IPs, or scheduled database update was added.
